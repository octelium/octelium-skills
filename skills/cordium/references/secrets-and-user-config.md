# Secrets, UserSecrets and UserConfig

Docs: https://octelium.com/docs/cordium/latest/overview/concepts.md

## Secrets (Space-scoped)

A Secret holds up to 1500 bytes. Its value is write-only: the API never returns it, and there is
no update call (delete and re-create to rotate). Creating, reading one and deleting need ADMIN
or OWNER; any Member can list names.

Create it so the value never appears in arguments, files or the transcript:

```bash
cordium create secret anthropic-key.agents                   # the user types it at the prompt
cordium create secret anthropic-key.agents --from-env ANTHROPIC_API_KEY
cordium create secret registry-token.agents -f -              # from stdin
cordium get sec --space agents
cordium delete sec anthropic-key.agents
```

`--value` puts the secret in shell history and process lists: don't use it. Without a TTY the
prompt can't run; ask the user to run the command in their terminal, or use `--from-env`/`-f -`
with a value they provide out of band. If a secret was pasted into chat, recommend rotating it.

References use the full name `<name>.<space>.<owner>` (`<name>.<space>.cordium` in organization
Spaces):

| Field | Purpose |
| --- | --- |
| `runtime.envVars[].fromSecret` (or `--env-from-secret KEY=<full name>`) | Environment variable in the Workspace and its tasks |
| `image.registry.authentication.password.fromSecret` | Private registry password |
| `repository.authentication.http.password.fromSecret` | Private repository token |
| GitProvider `clientSecret.fromSecret` (`--client-secret-from-secret`) | OAuth2 client secret |

Values are resolved at every start, so a re-created Secret reaches Workspaces on their next
start; a deleted one is silently skipped (the variable is missing). Inside the Workspace the
value is an ordinary environment variable that every process can read and print. For
credentials an agent must not see, or that exceed 1500 bytes (kubeconfigs, certificates,
private keys), protect the target as an Octelium Service with secretless credential injection
instead (octelium-management) and grant the Workspace owner access to it.

## UserSecrets (per User)

Names are `<name>.<you>`. Two types:

| Type | Value | Use |
| --- | --- | --- |
| `DEFAULT` | Provided by the User (up to 1500 bytes) | UserConfig env vars, dotfiles repository token |
| `SSH_KEY` | ECDSA key pair generated by the Cluster | The private key is loaded into the SSH agent of every Workspace of the User (`SSH_AUTH_SOCK`); register the public key with GitHub, GitLab or servers |

```bash
cordium create usersecret github-token                 # prompt
cordium create usersecret github-token --from-env GITHUB_TOKEN
cordium get usec deploy-key -o yaml                    # SSH_KEY: status.sshKey.publicKey
```

In v0.15.0 and the source checked, `cordium create usersecret <name> --type ssh-key` is rejected
with `Resource data must be set`: create SSH keys in the web console ("Your Secrets", type SSH).

## UserConfig (per User)

One UserConfig per User, created on first use and applied to all their Workspaces. There is no
CLI command: edit it in the web console settings (or `UpdateUserConfig`).

```yaml fragment
spec:
  dotfiles:
    url: https://github.com/alice/dotfiles
    branch: main
    authentication:              # private repositories only
      http:
        username: alice
        password:
          fromUserSecret: github-token.alice
  envVars:
    - key: EDITOR
      value: nvim
    - key: GITHUB_TOKEN
      fromUserSecret: github-token.alice
  tasks:
    - name: tools
      type: ON_CREATE
      run: pip install --user httpie
  preferredRegion: default
```

- **Dotfiles** are cloned to `~/dotfiles` at the start of `PREPARING` on fresh runs (not during
  pre-builds), then the first of `install.sh`, `install`, `bootstrap.sh`, `bootstrap`,
  `script/bootstrap`, `setup.sh`, `setup`, `script/setup` runs as the Workspace User.
- **Env vars** have the lowest precedence (Space, Template and Workspace values win).
- **Tasks** run after the Workspace and Template tasks and before the Space tasks.
- **preferredRegion** must be a Region enabled for Workspaces; it is used when storage doesn't
  pin the Region.
- `fromUserSecret` must be the full `<name>.<you>`.
